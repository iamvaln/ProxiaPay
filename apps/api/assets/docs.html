Integration guide · {{ENV}}

Taking and sending mobile money payments through ProxiaPay

Every payment is two calls — a preview, then a confirmation — and every outcome reaches you twice: as a state on the transaction you can retrieve at any time, and as a signed notification. Amounts are integers in the currency's minor units, timestamps are RFC 3339 in UTC, and every response carries an X-Request-Id to quote when you need help.

0

Your project

A project is what the platform knows you as. An administrator creates it in the console and hands you what is below, once, in writing. Fill this card in for your own team — it is stored only in this browser.

Never write the client secret or the notification signing secret here or anywhere but a secret store. Each is shown exactly once, when issued; a lost one is replaced, not recovered.

What each of these is

  • Credentials — a key (pk_test_… in sandbox, pk_live_… in production) and a secret. A project holds one primary credential; issuing a secondary begins a rotation, and revoking the old one ends it. Issuing takes a confirmation code on the administrator's side, so it cannot happen by accident.
  • Routes granted — a route is one country, one payment method, one currency, one direction. You can only pay on routes your project has been entitled to; each entitlement carries its own limits, velocity caps and fee terms, which you read from settings rather than from this card.
  • Declared origins — the addresses or ranges your product calls from. Production refuses any other origin before it even looks at your credentials. Sandbox does not require one.
  • Notification address — where events are delivered. An administrator sets it; a credential cannot. Its signing secret is shown once at that moment.
1

Credentials and tokens

Exchange the key and secret for a bearer token and carry the token on every other call.

POST {{SERVER}}/auth/tokens
{ "client_key": "pk_test_…", "client_secret": "sk_test_…" }

→ 200 { "access_token": "pt_…", "token_type": "Bearer", "expires_in": 3600 }

Hold the token. Exchange again when it is within a few minutes of expiry or when a call returns TOKEN_EXPIRED — and only then. Exchanging on every call exhausts the exchange limit (ten per minute per credential) and raises a security alert against your project. Each instance of your product holds its own token; tokens never invalidate one another.

Order of checks. Origin is verified before credentials. In production, a call from an undeclared address is refused with ORIGIN_NOT_ALLOWED before the secret is looked at — declare new infrastructure before it starts calling.
2

Read settings, do not hold configuration

GET {{SERVER}}/settings
Authorization: Bearer pt_…
If-None-Match: "…"        ← optional; a 304 costs nothing

The response lists, for every route your project holds: country, currency with its decimal exponent, payment method, direction, both fee rates with who bears them, amount limits, velocity caps and the payer action the route requires. Build your payment screens from this; nothing in your configuration should duplicate it.

Amounts everywhere are integers in minor units. XAF, XOF and GNF have no decimals — 1 000 XAF is 1000. CDF and USD have two — 10.50 USD is 1050. A decimal amount is refused with AMOUNT_INVALID, never rounded.

3

Preview, then confirm

POST /previewsfigures, normalised number, payer action, expiry
POST /collectionsor /disbursements — creates the transaction
processingor action_required, then succeeded / failed
notificationsigned; retrieve the transaction to act
POST {{SERVER}}/previews
{
  "direction": "collection", "amount": 1000, "currency": "XAF",
  "country": "CM", "payment_method": "MOMO",
  "counterparty": { "msisdn": "677123456", "name": "A. Mbarga" },
  "reference": "order-4417"
}

→ 201 { "reference": "prv_…", "requested_amount": 1000, "charged_amount": 1025,
        "settled_amount": 1000, "fees": { "processing": { "amount": 25, "bearer": "counterparty" },
        "platform": { "amount": 0, "bearer": "counterparty" }, "total": 25 },
        "payer_action": "none", "expires_at": "…" }

charged_amount is what the payer is debited on a collection (what your balance carries on a disbursement); settled_amount is what you receive (what the recipient receives). Show these figures. Never compute a fee yourself.

POST {{SERVER}}/collections          — or /disbursements
{ "preview_reference": "prv_…" }

→ 201 created now       → 200 an earlier confirmation created it; same transaction

Confirming twice is safe, and it is how you retry a call that timed out. A preview expires fifteen minutes after it is made.

reference is yours, unique within your project. Repeating a preview with the same reference and the same intent returns the original; a different intent under a used reference returns REFERENCE_CONFLICT. Your reference is what appears in your records and what support will search by.

4

Payer actions

payer_action in the preview tells you which of three sequences applies to the route.

payer_actionTransaction returns inWhat you do
noneprocessingNothing. The payer approves on their handset outside the platform.
codeaction_required with action.attempts_remainingCollect the code the operator sent the payer and submit it to POST /transactions/{reference}/code. A wrong code returns CODE_INVALID with the attempts left; exhausting them ends the transaction.
browseraction_required with action.urlSend the payer to that address. It authorises the payment for whoever holds it: it goes to the payer and nowhere else, and belongs in no log.
5

Notifications

Events arrive as a POST to your registered address with a JSON body and three headers.

POST https://your-product.example/hook
X-ProxiaPay-Event-Id: evt_…
X-ProxiaPay-Timestamp: 1789390744
X-ProxiaPay-Signature: 6f1c…           ← hex HMAC-SHA256

{ "id": "evt_…", "event": "transaction.succeeded", "occurred_at": "…",
  "data": { "transaction": { … } } }

Verify every one

  1. Compute HMAC-SHA256 over "{X-ProxiaPay-Timestamp}.{raw body bytes}" keyed on your signing secret, and compare it to X-ProxiaPay-Signature in constant time. Use the raw bytes: re-serialising changes whitespace and key order.
  2. Reject a timestamp more than five minutes from now.
  3. Delivery is at-least-once. An id you have already processed is acknowledged with 2xx and ignored.
// Node.js
const crypto = require('node:crypto');
function verify(secret, headers, rawBody) {
  const ts = Number(headers['x-proxiapay-timestamp']);
  if (!Number.isFinite(ts) || Math.abs(Date.now() / 1000 - ts) > 300) return false;
  const expected = crypto.createHmac('sha256', secret).update(`${ts}.`).update(rawBody).digest('hex');
  const given = String(headers['x-proxiapay-signature'] ?? '');
  return expected.length === given.length && crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(given));
}

Respond 2xx promptly. Anything else is retried on a widening interval, from one minute up to a day, eight attempts. A notification says a transaction's state may have changed: where the outcome governs something consequential, retrieve the transaction and act on what the retrieval returns.

Handle transaction.corrected. It means a payment previously reported one way turned out to be another — most consequentially, a collection reported as failed that the customer completed. It carries previous_state and previous_failure_reason beside the corrected transaction. A product that ignores it leaves an order unfulfilled against a customer who paid.
6

Errors: what to retry

Every error body is { "error": { "code", "message", "retryable", "details"? } }. retryable says whether repeating the identical request could succeed later.

SituationWhat to do
A preview call timed outRepeat it with the same reference; you get the original or REFERENCE_CONFLICT.
A confirm call timed outRepeat it with the same preview reference; you get the transaction the first call created.
TOKEN_EXPIREDExchange and retry.
RATE_LIMITEDWait for Retry-After. Every response carries X-RateLimit-* headers.
FLOAT_INSUFFICIENT, NO_PROVIDER_AVAILABLERetry later, unchanged. Both are the platform's condition, not yours.
BALANCE_INSUFFICIENTYour balance is short by details.shortfall; fund it or reduce the amount.
VELOCITY_COUNT_EXCEEDED, VELOCITY_VALUE_EXCEEDEDWait until details.resets_at.
SIMILAR_PAYMENT_PENDINGA matching payment is open; details.transaction names it. Do not raise another.
A transaction is undeterminedWait. Never send it again. The money may have moved; the resolution arrives by notification.

OUTCOME_UNDETERMINED is the one failure reason a product must never answer by repeating the payment.

Support

A customer contacting your support usually quotes the reference from their operator's confirmation message. That is operator_reference on the transaction, and GET /transactions?operator_reference=… finds it. Quote X-Request-Id from any response when raising a question with the platform team; it identifies the exact call.

Sandbox behaviour

In the sandbox a simulator stands in for the mobile money provider and chooses its behaviour by the last two digits of the counterparty number. Use these to exercise every branch of your handling before requesting production credentials.

Number ends inBehaviour
00Rejected at submission — WALLET_NOT_FOUND
01Accepted, then fails — PAYER_DECLINED
02Stays processing until the sweep ceiling, then undetermined
03Provider unreachable; fallback applies
04Submission times out; undetermined at once
05Accepted, then WALLET_BALANCE_INSUFFICIENT
06Requires a one-time code; the code is 123456
07Requires a browser step; completes on its own after about twenty seconds
anything elseSucceeds after a few seconds, at a 2 % provider fee
