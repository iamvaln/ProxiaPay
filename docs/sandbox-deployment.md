# Deploying the sandbox

The sandbox is `https://sandbox.pay.proxia-digital.com`, one stack among several
on a shared VPS (`77.237.234.91`). It runs the simulator adapter and holds no
real money, no real payer and no provider credentials.

Production on `pay.proxia-digital.com` is a separate stack that does not exist
yet. Where the two would differ, this document says so rather than leaving the
sandbox's shortcuts to be copied by accident.

## What runs

| Service | Command | Public |
|---|---|---|
| `db` | `postgres:16-alpine`, volume `proxiapay-sandbox_proxiapay-db` | no |
| `migrate` | `node dist/cli/migrate.js`, runs to completion, then exits | no |
| `api` | `node dist/main.js` — `/v1`, `/console`, `/providers`, `/docs`, `/healthz` | yes |
| `worker` | `node dist/main.worker.js` — the sweep, deliveries, reconciliation, alerts, float cover | no |
| `console` | the Vite bundle on nginx | yes |

`api` and `worker` boot from one image (`apps/api/Dockerfile`), differing only in
command, as spec 15.1 describes. `migrate` is a service of its own rather than a
step inside the API's start-up, because two processes racing the same migration
is a deadlock waiting for a busy morning.

There is no backup sidecar. Sandbox data is simulator data, regenerated by the
seed; a nightly dump nobody would ever read is not worth another bucket to keep.
Production will need one — see `docs/operations.md`.

## One hostname

The console's only call to the platform is relative — `fetch(\`/console${path}\`)`
in `apps/console/src/lib/api.ts` — so the bundle and the API must answer on the
same origin. Traefik splits them by path on the single host:

- `/v1`, `/console`, `/providers`, `/docs` → `api` (router priority 100)
- everything else → `console` (router priority 1), which serves `index.html` for
  any path that is not a file, so a refresh on a client-side route works.

The priorities are explicit rather than left to Traefik's rule-length tie-break:
the tie-break is documented behaviour, but an edit to either rule would silently
reorder them.

This also keeps the console image free of any baked-in address, so the same
build is correct in every environment — unlike the other projects on this VPS,
whose bundles carry their API URL and cannot be promoted between environments.

## The certificate

`CERT_RESOLVER=le` — Let's Encrypt over TLS-ALPN-01, which needs the name to
reach the VPS directly. It does: `sandbox.pay.proxia-digital.com` is a plain A
record, while the apex sits behind Cloudflare.

**The day this name goes behind Cloudflare's proxy, change it to `le-dns`.**
Cloudflare terminates TLS itself, so the ALPN challenge never reaches Traefik.
The failure is silent — the site serves perfectly on its existing certificate
until the renewal sixty days later.

## First-time setup on the VPS

Done once. The shared Traefik and the `web` network already exist.

```sh
ssh deploy@77.237.234.91
git clone https://github.com/iamvaln/ProxiaPay.git ~/proxiapay-sandbox
cd ~/proxiapay-sandbox && git checkout develop

cp deploy/sandbox.env.example .env.sandbox
chmod 600 .env.sandbox
nano .env.sandbox        # fill in every <…>; see the notes in the file itself
```

Generate the four secrets separately — none of them is shared with any other
environment, and a sandbox token that opens production is the kind of shortcut
taken "for now" that never gets undone:

```sh
openssl rand -hex 24      # POSTGRES_PASSWORD, repeated inside DATABASE_URL
openssl rand -base64 32   # MASTER_KEY_BASE64
openssl rand -base64 32   # INDEX_KEY_BASE64
```

Then bring it up and seed it:

```sh
docker compose --env-file .env.sandbox -f docker-compose.deploy.yml up -d db migrate api worker console

# Reference data: the catalogue, roles, alert routing, and the simulator
# provider account that PROXIAPAY_ENV=sandbox selects.
docker compose --env-file .env.sandbox -f docker-compose.deploy.yml run --rm migrate node dist/cli/seed.js

# Your administrator. The first sign-in enrols an authenticator.
docker compose --env-file .env.sandbox -f docker-compose.deploy.yml run --rm migrate \
  node dist/cli/create-admin.js --name "Your Name" --email you@example.com --password 'a long passphrase'
```

## Deploying afterwards

Merging to `develop` is the whole procedure. `.github/workflows/sandbox.yml`
builds both images to `ghcr.io/iamvaln/proxiapay-{api,console}:develop`, deploys
over SSH, and then checks that `/healthz` answers 200 before it calls the run
green. `workflow_dispatch` redeploys without a commit, after a VPS reboot say.

Three repository secrets make it work: `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`
(and `VPS_PORT` if it ever stops being 22).

By hand, if CI is unavailable:

```sh
cd ~/proxiapay-sandbox && git pull
docker compose --env-file .env.sandbox -f docker-compose.deploy.yml pull db api worker console
docker compose --env-file .env.sandbox -f docker-compose.deploy.yml up -d db migrate api worker console
```

### The Compose project name

`docker-compose.deploy.yml` sets `name: ${STACK:-proxiapay}`, and the deploy
workflow asks Compose to confirm that name before it touches anything.

This is not ceremony. A project name frozen in the file makes *every directory
holding a checkout drive the same Compose project*: an `up` run from the sandbox
directory recreates the production containers, with the sandbox's environment and
images. That is exactly what happened to another project on this VPS on 14
September — production answered 404 until someone restarted it. The guard costs
one read and removes the possibility.

If `STACK` were missing from `.env.sandbox`, the name would fall back to
`proxiapay` and the guard would stop the deploy.

## Where the keys live, and why that is a deviation

`docs/operations.md` is explicit: `MASTER_KEY_BASE64` and `INDEX_KEY_BASE64`
should be injected from a key store at process start and never sit in a file on
the host. On this VPS they sit in `~/proxiapay-sandbox/.env.sandbox`, mode 600.

The reasons this is acceptable *here* are the reasons it will not be acceptable
in production: the sandbox seals nothing but simulator traffic, its database is
regenerated from the seed, and the loss of both keys costs a re-seed. Production
seals real payer identifiers and real provider credentials, and a database
restored without its keys yields records nobody can read.

**Production must not inherit this file or this arrangement.** Standing it up
includes choosing where its keys come from.

## Checking it

```sh
curl -s https://sandbox.pay.proxia-digital.com/healthz            # {"status":"ok"}
curl -sI https://sandbox.pay.proxia-digital.com/                  # the console, 200
open https://sandbox.pay.proxia-digital.com/docs                  # the integration guide
docker compose --env-file .env.sandbox -f docker-compose.deploy.yml ps
docker compose --env-file .env.sandbox -f docker-compose.deploy.yml logs -f api worker
```

`/healthz` reports on the process and takes no dependencies. A probe that read
the database would call the process dead during a database outage and Compose
would restart something that was answering perfectly well. What the sandbox can
actually *do* is a different question, and the console's own screens (spec 8.5)
answer it with far more than a boolean.

## Keeping `.env.sandbox` in step

`git pull` does not touch it — it holds the real secrets and is ignored. When a
release adds a variable, it appears in `deploy/sandbox.env.example` and not in
the live file, and the service that wants it starts with a default or a warning.

```sh
diff <(grep -v '^\s*#' deploy/sandbox.env.example | grep '=' | cut -d= -f1 | sort) \
     <(grep -v '^\s*#' .env.sandbox                | grep '=' | cut -d= -f1 | sort)
```

Anything on the left ("<") is missing from the live file. Add it before `up -d`.
